# Product

## Platform

web

## Stack

React + Vite + TypeScript, SPA. Код разложен по чистой архитектуре: domain (сущности и правила форм), application (порт `ClearanceApi` и сценарии), infrastructure (HTTP-клиент), presentation (React). Фронтенд работает только с настоящим API, моковых данных нет. Контракт: `docs/backend/openapi.yaml`, ТЗ для бэкенда: `docs/backend/README.md`. Бэкенд пишется отдельно (стек на выбор, PostgreSQL). Вход по логину и паролю колледжа, сессия в httpOnly-cookie.

## Users

- **Студент колледжа** уходит из колледжа или общежития (выпуск, отчисление, перевод, академический отпуск, выселение) и должен закрыть обходной лист. Сейчас он ходит по 5–7 кабинетам и узнаёт о долгах у двери. Чаще всего заходит с телефона.
- **Сотрудник отдела** (библиотека, бухгалтерия, общежитие, военно-учётный стол, IT-отдел, учебная часть) подтверждает, что у студента нет задолженности, или указывает конкретный долг. Работает за рабочим компьютером, обрабатывает пачки листов в сезон выпуска.
- **Администратор учебной части** создаёт обходные листы, настраивает шаблоны (какие отделы входят в лист каждого типа), видит общую картину и зависшие листы.
- **Проверяющий** (отдел кадров, другой колледж, работодатель) открывает публичную страницу по QR-коду с PDF и проверяет подлинность закрытого листа. Аккаунта у него нет.

## Product Purpose

Заменить бумажный обходной лист электронным. Отделы ставят отметки параллельно, студент видит в реальном времени, какой отдел его держит и что нужно сделать. Закрытый лист выдаётся в PDF с QR-кодом для проверки подлинности.

Успех: студент оформляет обходной за день вместо нескольких, отделы заранее видят должников.

Проект делается как учебный (производственное обучение, группа из 4 человек) и оценивается по критериям бизнес-анализа, требований, технической документации, реализации и тестирования.

## Positioning

В колледжах Казахстана электронного обходного листа нет: абитуриенты подают документы через eGov, студенческие билеты цифровые, а обходной остаётся бумажным. Сервис делает процесс параллельным вместо последовательного и даёт студенту прозрачный статус по каждому отделу.

## Operating Context

- Типы обходного листа: выпуск, отчисление, перевод, академический отпуск, выселение из общежития. У каждого типа свой набор отделов (шаблон).
- Статусы листа: создан → в работе → есть задолженность → закрыт. Отметка отдела: ожидает / нет задолженности / есть задолженность (с описанием и сроком).
- Закрытый лист менять нельзя. Лист не закрывается, пока есть открытая задолженность. У студента не может быть двух активных листов одного типа.
- Каждый отдел видит и меняет только свою отметку. Все изменения отметок пишутся в журнал аудита.
- Уведомления студенту дублируются в Telegram.
- Пиковая нагрузка весной (выпуск), остальные типы идут весь год.

## Capabilities and Constraints

- Роли: студент, сотрудник отдела, администратор учебной части; публичная страница проверки без авторизации.
- Публичная страница проверки показывает минимум данных: ФИО, тип листа, дату закрытия, статус подлинности.
- Интеграций с 1С и библиотечными системами в MVP нет: сотрудник отмечает долги вручную. Это ограничение фиксируется в документации.
- Интерфейс на русском и казахском с переключателем языка.
- Вход: логин и пароль, которые выдаёт учебная часть; временный пароль нужно сменить при первом входе.

## Product Principles

1. Студент всегда знает, что именно его держит и что сделать дальше.
2. Сотрудник отдела закрывает отметку за секунды; массовая обработка важнее красоты.
3. Закрытый лист неизменяем и проверяем: доверие к документу важнее удобства правок.
4. Каждая роль видит только своё.
5. Не обещать того, чего нет: никаких выдуманных цифр и клиентов.

## Accessibility & Inclusion

Два языка интерфейса (русский, казахский). Студенческий кабинет рассчитан в первую очередь на телефон. Цель WCAG 2.1 AA: контраст, клавиатурная навигация, понятные тексты ошибок.
